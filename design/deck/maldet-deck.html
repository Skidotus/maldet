Final Year Project · Diploma in Cyber Security Technology

Know what a repository hides before you run it.

MalDet scans a public GitHub repository with six detection engines and returns two verdicts: how exploitable the code is, and whether it looks like it means harm.

Haikal · Ariff · Aleena · Adam Supervisor Sir Luqman German-Malaysian Institute maldet-fyp.my

The problem

Everyone installs code they have not read.

A developer adds a dependency, clones a tool, copies a script. The decision takes seconds and is made on stars, a readme and a feeling. The code that arrives runs with their permissions, on their machine, against their data.

The tools that could answer the question exist and are free. They are also five separate programs with five output formats, five severity scales, and tens of thousands of lines of results. Nobody runs them for a repository they were only mildly unsure about.

MalDet's value is the aggregation and the triage, not a new detection technique. Each engine it runs is open source and could be run by hand.

The idea

One number hides the thing you need to know.

“Risky” is two different questions. A repository can be full of exploitable mistakes and entirely well meant, or clean and quietly hostile. Collapsing both into a single score hides which one you are looking at, so MalDet never does.

Vulnerability

Insecure patterns an attacker could exploit. Bandit, Semgrep, and CVE lookups against the declared dependencies.

Malicious pattern

Signs the code is trying to do something hostile. YARA rules, ClamAV, typosquats, install-time hooks, direct-URL installs.

Each axis is scored and calibrated separately. Malicious-pattern findings are far rarer than vulnerability ones, and a shared scale made them read as artificially mild.

How it works

Six engines, one pipeline.

CloneShallow clone, archives extracted
BanditPython security linting
SemgrepMulti-language patterns
YARAMalware signatures
ClamAVKnown malware
GuardDogPackage heuristics
DependenciesCVEs, typosquats, hooks
VerdictFilter, classify, score both axes

Engines run in sequence, one scan at a time. That is a memory constraint, not a design preference: Semgrep alone peaks near 2GB, and the deployment target has 4GB.

The real problem with running five tools

78%of all findings are noise

Aggregation alone makes it worse.

Six engines across 181 repositories produced 63,598 findings. Most are boilerplate: a test fixture, a hardcoded localhost, an import that looks like an import. Handing a developer all of them is not better than handing them none.

A Random Forest classifier scores every finding for whether it is real, and that confidence weights the risk score rather than every finding counting equally.

49,747 of 63,598 findings score below 0.3 confidence; 9,463 score at or above 0.5. Corpus measured 30 October 2026.

The classifier, honestly

Modest numbers, measured properly.

0.52Precision
0.62Recall
0.28Baseline precision
(treat every finding as real)

Measured against 168 findings reviewed by hand, not against the classifier's own training labels. F1 is 0.56. Roughly double the baseline at finding what matters.

Two disclosures. The classifier is weakly supervised — its training labels come from frequency heuristics, not human review, so the much higher figures train_classifier.py prints are it grading its own homework and are not quoted here. And the 168 hand labels were produced by an AI-assisted first pass confirmed by the author, not by independent review.

Beyond the website

The verdict, where the decision is made.

The judgement is wanted while you are looking at a repository, not after remembering a tool exists. A browser extension, signed by Mozilla, puts it on the GitHub page itself: whether MalDet has seen this repository, and how long ago.

It reports when a repository was scanned, never a risk level. A scan is a snapshot and the code keeps changing after it — an age is honest where a score pinned to someone else's page would not be.

Declared to Mozilla as collecting browsing activity, because it is: the repository name is sent to the server to ask the question. The server does not record it.

What it does not do

The limits, stated up front.

Static analysis only. Nothing is executed. Malware that only reveals itself at runtime will not be seen.
Public repositories only. No accounts, no private repositories, no organisations. A permanent shape, not a missing feature.
Python and Node manifests. Go, Rust, Java and others are cloned and scanned, but their dependency files are not parsed.
A snapshot, not monitoring. A verdict describes the repository on the day it was scanned.
Precision 0.52 is not a solved problem. About half of what it flags as real still is not. It is a triage aid, not an oracle.

Six engines. Two verdicts. One scan.
